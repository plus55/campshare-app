## Architectural notes from this session

User asked a strategic question: is the codebase scalable, and is the Rails-marketplace pattern necessary? **Answer documented in Second Brain wiki** at `9-Wiki/syntheses/marketplace-stack-choices.md`.

**Hardening pulled forward to S10:**
- Booking atomicity — wrap booking insert + booking_addon inserts + availability_block insert in `db().batch([...])` to prevent partial state on failure (currently 4 separate writes after Stripe capture).
- Race on availability — same check-then-insert pattern; should add UNIQUE constraint or atomic batch.
- Turnstile on `/signup` and `/apply`.
- Cloudflare rate-limit rules on `/api/auth/*` and `/api/bookings`.

## Non-obvious things this session

- `BookingRequestForm.tsx` had to be split into a gate + `BookingRequestFormInner` because react-hooks rules forbid the early return appearing before hook calls.
- Stripe Identity DOB is in `verified_outputs.dob` which requires `expand: ['verified_outputs']` on retrieve — webhook payload doesn't include it by default.
- The booking detail page admin link in `/admin/reports` uses `/admin/bookings/[id]` — that route doesn't exist yet. Either build it later or change the link to `/dashboard/bookings/[id]` (admin can view via host UI since admins are typically also hosts).
